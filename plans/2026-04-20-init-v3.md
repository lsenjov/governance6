# Governance — Online Game Application

## Objective

Deliver **Governance**, a multiplayer web app in which users author reusable **Syndicates** (with Minions and drawbacks), run live game sessions as a Game Master (GM), and — as Players — manage POWER, buy Minions, and queue Calls. The app must support live multi-user updates during a `playing` game, enforce role-based permissions (GM vs Player vs author), and persist a full audit trail of POWER changes.

## Stack (locked in)

- **Frontend**: Vite + React + TypeScript. Client-side routing via React Router.
- **Backend, database, real-time**: Convex. Reactive queries drive all multi-user live views (POWER, Call Queue, game state, elapsed time). Mutations are transactional by default, neutralising race-condition risk on POWER edits, Minion buys, and Call replacements.
- **Auth**: Convex Auth with the Password provider (email + password, open self-registration).

## Confirmed Rules (from requirements brief and Q&A)

These are the authoritative game rules. Every implementation task below is traceable to one of these or to the original brief (`plans/init.md`).

1. **User display name** — editable any time on a profile page. **No uniqueness constraint**; duplicates allowed.
2. **Syndicate** — has `name`, `leader` (string), `description`, `played` boolean (default `false`), `isShared` boolean (default `false`), and an owner.
3. **Drawbacks** — each has a `name` and `description`. **0–5 per Syndicate.**
4. **Minions per Syndicate** — up to **8**. Each has a **mandatory** `name`, **optional** `accent` (free text), **optional** `description`, and **1–5 skills** (each a single string).
5. **Edit-lock rule** — a Syndicate and its Minions + Drawbacks are editable by the owner **only while `played=false`**. Once `played=true`, the Syndicate is frozen permanently but remains selectable in future games.
6. **`isShared` rule** — owner can toggle in either direction **while `played=false`**; it controls whether *other* users can select the Syndicate in their games. It does **not** lock editing. Once `played=true`, `isShared` is frozen at its current value.
7. **`played` flag** — purely informational; set automatically to `true` on every selected Syndicate when a game leaves `ready`. It does not force `isShared`, does not bar reuse in future games; it merely freezes content (rule 5).
8. **Edits while selected in a ready game** — allowed (since `played=false`); changes propagate live to the selecting Player via Convex reactivity.
9. **Game** — owned by a GM. State enum: `ready` → `playing` → `archived` (both `ready → archived` and `playing → archived` allowed, **manual GM button only**).
10. **GM ≠ Player** — the GM of a game **cannot** also be a Player in that same game. The "add Player" picker excludes the GM.
11. **Roster changes** — GM can add/remove Players only while `ready`. While `playing`, removal is **disallowed**; Players remain until archive.
12. **Syndicate selection** — during `ready`, a Player may select any Syndicate they own, or any Syndicate with `isShared=true` (including their own). Selection is editable until `ready → playing`.
13. **Lifecycle side-effect** — on `ready → playing`, the game's `startedAt` is stamped with server time and every selected Syndicate has `played` set to `true` atomically.
14. **Elapsed time** — while `playing`, all viewers see a live elapsed-time display derived from `startedAt`.
15. **POWER** — integer, starts at `0` for every Player. GM may set any value at any time, with an **optional** reason (per `plans/init.md:28`). POWER can go negative.
16. **Ledger** — append-only. Every change to POWER writes a ledger entry (delta, optional reason for GM edits, required reason for transfers, source tag, counterparty if any, timestamp).
17. **Transfers**
    - Player → Player: positive amount, **reason required**.
    - Player → Bank: positive amount, **reason required** (burns POWER into the bank).
    - Bank is an **infinite, GM-controlled, per-game pool**; GM grants are sourced from the bank. No stored balance on the bank.
18. **Ledger visibility**
    - A Player sees their **own** ledger in full (line items with reasons and counterparties).
    - The **GM** sees every Player's full ledger.
    - Other Players see only each Player's current **balance**, never line items.
19. **Minion buy (in-game)** — per-game state on a join row (`gamePlayerMinions`). The first Minion is free; subsequent buys cost `2, 4, 6, 8, 10, 12, 14`. Exact sequence for the 1st through 8th Minion bought: `0, 2, 4, 6, 8, 10, 12, 14`. The buy writes a ledger entry for the deducted POWER.
20. **Call Queue** — per game.
    - FIFO by add time.
    - A Player may have **at most one** active Call at a time.
    - Adding a new Call while one exists **replaces** the existing one **in place**, preserving its original queue position and original `createdAt`.
    - A Player may only add a Call for a Minion they have **bought** in this game.
    - GM may remove any Call; removed Calls appear in a **history of the last 10 removed Calls**.
21. **Authorisation** — enforced server-side in Convex mutations/queries regardless of UI state. Three effective roles per resource: owner (author / GM), participant (Player in a game), viewer (authenticated user).

## Verification Criteria

- A new user can register, set a (non-unique) display name, create a Syndicate with 0–5 drawbacks and up to 8 Minions (each with 1–5 skills), and toggle `isShared` on and off while `played=false`.
- Every mutation that edits a Syndicate, Drawback, or Minion fails with an authorisation error when the parent Syndicate has `played=true`. `isShared` alone never blocks edits.
- A GM can create a game, add/remove Players while `ready`, and Players can select either an owned Syndicate or any `isShared` Syndicate. A GM cannot be added as a Player to their own game.
- `ready → playing` atomically stamps `startedAt` and flips `played=true` on every selected Syndicate; if any step fails the whole transition rolls back.
- All clients viewing a `playing` game see elapsed time within one second of each other, updating continuously.
- POWER starts at `0` for every Player. GM edits, Player→Player transfers, Player→Bank transfers, and Minion buys each produce correct ledger entries; the ledger exposes no update/delete endpoints.
- Transfers (Player→Player and Player→Bank) reject empty/whitespace reasons and non-positive amounts.
- POWER can go negative (no floor check).
- Buying the 1st–8th Minion for a Player in a Game costs exactly `0, 2, 4, 6, 8, 10, 12, 14` POWER respectively; each purchase writes a matching `minion_buy` ledger entry.
- A Player cannot hold more than one active Call. Calling a second time updates the existing Call's `minionId` in place, keeping its `createdAt` (FIFO position) unchanged.
- GM-removed Calls appear in the removed-history view, capped at the 10 most recent.
- Ledger visibility: Player A sees own full ledger, sees Player B's balance only; GM sees every ledger in full.
- Roster changes are disallowed while `playing`. `ready → archived` and `playing → archived` are GM-only.
- Authorisation tests prove: non-GMs cannot transition state, edit POWER, or remove Calls; non-authors cannot edit Syndicates; non-Players cannot buy Minions, add Calls, or transfer POWER; users outside a game cannot read its private data.

## Potential Risks and Mitigations

1. **Race conditions on POWER, Minion buys, and Call replacement.**
   Mitigation: every mutation is a single Convex transaction reading and writing all affected documents; no multi-step non-transactional sequences.
2. **Convex Auth is still labelled beta.**
   Mitigation: isolate auth calls behind the `convex/lib/auth.ts` helper so swapping to Clerk later is mechanical if needed.
3. **Replace-in-place Call semantics (rule 20) are easy to get wrong by re-inserting.**
   Mitigation: dedicated test (Task 46); explicit code comment linking to rule 20.
4. **`played`-lock drift**: it's tempting to also lock on `isShared`; the rules reject that (rule 6).
   Mitigation: a single `assertSyndicateEditable(syndicateId)` helper used by every mutation, which asserts on `played` only; covered by tests.
5. **Ledger visibility leak.**
   Mitigation: never expose raw `powerLedgerEntries` in a query; provide only the three scoped queries from Task 28.
6. **Live updates subtly missing** because a component fetched through a non-reactive path.
   Mitigation: lint rule or code review checklist enforcing `useQuery` for all game-page data; Playwright test asserts cross-context updates.
7. **Uniqueness of `(gameId, userId)` on players** if not enforced can allow the same user twice.
   Mitigation: Convex schema index + an explicit guard in `addPlayer`.
8. **GM-as-Player** slipping in via a direct `addPlayer` call.
   Mitigation: server-side check in `addPlayer` rejecting the GM (Task 18); covered by Task 45.
9. **N+1 queries** when rendering game pages with many Players, Minions, Calls, ledger rows.
   Mitigation: denormalise hot reads (e.g. `players.power` mirror) and design queries to fetch in bulk; paginate ledger views.

## Alternative Approaches (historical — stack is locked)

The following were considered and rejected in favour of Convex + Vite + React:

1. **Phoenix LiveView** — excellent real-time, but not TypeScript.
2. **Rails + Hotwire** — mature, but heavier infra and no first-party TS.
3. **Next.js + Convex** — viable, but SSR is unnecessary for an auth-gated game app and adds deploy complexity over a static Vite SPA.
4. **REST + polling** — simpler, but loses the live-updating Call Queue and elapsed-time UX that Convex gives almost for free.

## Domain Specification (preserved from `plans/init.md`)

Retained verbatim for traceability. The confirmed rules above take precedence where they refine or clarify this text.

- Each user has a display name, which can be changed at any time from a profile page.
- A user can create Syndicates. Each Syndicate has a name, leader and description. Each Syndicate has a `played` boolean, default `false`. Each Syndicate has a number of drawbacks (name + description). Each Syndicate has an `is-shared` boolean, default `false`; if true, users cannot modify details of the Syndicate or Minions.
- Each Syndicate has up to 8 Minions. Each Minion has a mandatory name, optional accent, optional description, and 1–5 skills (each a single string).
- Users can create a game; the owner is the GM. Games have state (`ready`, `playing`, `archived`); all users see status, only the GM can change it.
- Games have a start time, nil by default. The game tracks when it moves to `playing` and displays elapsed time to all users while `playing`. While `ready`, the GM can add/remove Players. While `ready`, a Player can select any own Syndicate, or any Syndicate with `is-shared=true`. When the game leaves `ready`, all selected Syndicates have `played` set to `true`.
- Each Player has integer POWER (GM-editable). Each Player has a ledger of POWER income and expenditures with an optional reason. POWER can go negative. A Player can send a positive amount of POWER to any other Player or the bank, with a reason.
- In each game, each Player sees their own Minions and whether they've been bought; they can buy Minions. First Minion is free; subsequent prices are 2/4/6/8/10/12/14.
- Each game has a Call Queue. A Player can add a bought Minion; only one Call per Player (new replaces old). GM can remove calls. A removed-calls history shows the last 10.
