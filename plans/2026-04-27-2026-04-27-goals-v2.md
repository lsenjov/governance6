# Goals

> **Change from v1**: `from_player` is **optional** at Goal creation. The schema, validation, `assignToPlayer` authorisation, visibility rules, UI, tests, and Rule 28 documentation are all updated to treat `from_player` symmetrically with `to_player` (both optional, both clearable by the GM via the explicit `null`-arg convention). Only the GM can set, change, or clear `from_player` in v1; Players cannot self-claim a Goal as its `from_player` (out of scope for v1; documented in Alternative 7).

## Objective

Add a new per-game asset class — **Goals** — to Governance. A Goal is a `(keyword, description, type, from_player?, to_player?, carrot?, stick?)` bundle attached to a single game. Goals describe (potentially-)directed obligations between Players (with optional shared / competitive variants) and carry a non-negative POWER reward (`carrot`) and/or a non-positive POWER penalty (`stick`) that the GM can later apply by hand using existing POWER edit flows.

The GM has full read/write permission on every Goal at all times. Other Players see every Goal in the game with all fields **except `description`**, which is redacted unless the viewer is the Goal's current `from_player` or `to_player`. A `from_player` may assign a `to_player` themselves while the Goal is still missing one; otherwise only the GM may set or change `to_player`.

This feature must integrate cleanly with:
- the rule-bound game lifecycle (`convex/games.ts`, rule 10 in `plans/2026-04-20-init-v4.md:26`),
- centralised authorisation helpers (`convex/lib/auth.ts:53-125`, rule 24 in `plans/2026-04-20-init-v4.md:52`),
- the existing per-game asset module conventions established by Treason Grants (`convex/treasonGrants.ts:1-387`, `plans/2026-04-27-treason-grants-v1.md`),
- the `GameDetailPage` main-column section pattern (`src/pages/GameDetailPage.tsx:96-151`, `src/pages/GameDetailPage.tsx:1907-1980`).

## Confirmed design decisions

These decisions resolve the ambiguities in the feature request and become the authoritative interpretation for this plan. Each decision cites the assumption it codifies so the implementation agent can revisit them if a stakeholder objects.

1. **Scope**: per-game. Each Goal carries a `gameId`. Goals do not cross games. Mirrors `treasonGrants` per `convex/schema.ts:189-205`.
2. **Player references**: `from_player` and `to_player` are both `v.optional(v.id("players"))`, per-game refs (never `Id<"users">`). Matches `treasonGrants.ownerPlayerId` (`convex/schema.ts:198`) and rule 11 (GM ≠ Player, `plans/2026-04-20-init-v4.md:27`) — the GM cannot be a `from_player` or `to_player`.
3. **Authoring**: GM creates Goals. Only the GM may set, change, or clear `from_player` in v1 (via `createGoal` / `updateGoal`). Players cannot claim themselves as `from_player`; if a stakeholder later wants a "volunteer for this goal" flow, see Alternative 7.
4. **Lifecycle states for GM CRUD**: allowed in `ready` and `playing`. Disallowed in `archived`. Mirrors Treason Grants Decision 4.
5. **`from_player` assigns `to_player`** (Player-driven path):
    - Allowed iff `goal.fromPlayerId !== undefined`, `goal.toPlayerId === undefined`, the caller's `playerId === goal.fromPlayerId`, and the game is not `archived`.
    - The new `to_player` must reference a Player in this game and must not equal `from_player`.
    - Once `to_player` is non-null, only the GM may change or clear it.
    - If `from_player` is **unset**, no Player has this affordance — only the GM can assign `to_player` (via `updateGoal`). The Player-driven `assignToPlayer` mutation rejects every Player call for a Goal whose `from_player` is missing, with the message `"This Goal has no from-player; only the GM can assign a to-player."`.
6. **Type semantics for v1**: `type` is a presentational tag only. It governs the keyword display suffix per the spec but does **not** alter visibility, permissions, or POWER mechanics. Decoupling type from rules keeps the per-Player visibility rule (description gated on from/to) the single source of truth and means the type can be reinterpreted later without a schema migration.
7. **Carrot / Stick semantics for v1**: descriptive labels only. They are stored on the Goal and displayed per the formatting rules below, but **no automatic ledger entries** are written when a Goal is "completed" or "failed". The GM applies rewards/penalties using the existing rule-20 POWER edit flow. Rationale: the original spec does not define a completion mechanic; this plan refuses to invent one and instead leaves the audit trail under the GM's explicit control, consistent with rule 17 and rule 19 (`plans/2026-04-20-init-v4.md:33-35`). Decision can be revisited in a v2 plan.
8. **GM full permissions**: the GM may create, edit any field (including setting/clearing `from_player`, `to_player`, `type`, `carrot`, `stick`), and delete in any state except `archived` (which is read-only by Decision 4). The GM may always view every field on every Goal.
9. **Visibility**:
    - GM: sees all fields on all Goals in any state.
    - Player: sees `keyword`, `type`, `from_player` (with display name, or `null`), `to_player` (with display name, or `null`), `carrot`, `stick`, and `createdAt` on every Goal.
    - Player sees `description` **only** when they are the current `from_player` or the current `to_player`. To everyone else (including non-from/to Players) the description is `null` (redacted). When *both* `from_player` and `to_player` are `undefined`, no Player sees the description; only the GM does. Non-participants are rejected outright (rule 24).
    - The placeholder for redacted descriptions is identical regardless of why it is hidden, so a Player cannot infer the existence or absence of from/to assignments from the placeholder text (mirrors Treason Grants Risk 1).
10. **Validation**:
    - `keyword`: trimmed, 1–40 chars, **unique within a game** (case-insensitive). Mirrors `treasonGrants.keyword` (`convex/treasonGrants.ts:39-61`).
    - `description`: 0–2000 chars (matches `notes` and `treasonGrants` ceilings). Empty allowed.
    - `type`: one of `"regular" | "shared" | "competitive"`. Required. Default in the create form: `"regular"`.
    - `from_player`: optional `Id<"players">`; if present, must reference a Player row whose `gameId === goal.gameId`. Cross-game references rejected.
    - `to_player`: optional `Id<"players">`; if present, must reference a Player in the same game and must not equal `from_player` (when `from_player` is also set).
    - `carrot`: optional integer; if present, `0 ≤ carrot ≤ 1000` (sanity bound, matches POWER bound used in `treasonGrants`).
    - `stick`: optional integer; if present, `-1000 ≤ stick ≤ 0`.
    - Storing `carrot === 0` or `stick === 0` is permitted but, per the display rules, a stored `0` is treated the same as "absent" by the formatter (see rule 11). The create/edit form omits the field entirely when the user clears the input rather than writing a `0`. Server validates either way.
11. **Display formatting** (server returns the raw values; the client formats):
    - **Keyword suffix**: `regular → "<KEYWORD>"`, `shared → "<KEYWORD> (S)"`, `competitive → "<KEYWORD> (C)"`. Case of `(S)` / `(C)` is fixed (capital).
    - **Carrot/Stick shorthand**:
        - both present (and at least one non-zero): `"<carrot>/<stick>"`, e.g. `"15/-10"`,
        - only `carrot` present: `"<carrot>"`,
        - only `stick` present: `"<stick>"`,
        - neither present **or both `0`**: `"---"`.
        - "Present" means the field is a finite integer and not `0` for display purposes; `0` is rendered as absent. This matches the user's intent ("If there is no carrot or stick, display it as `---`").
    - **From / To labels**: when the player ref is unset, render `Unassigned` in muted styling.
12. **Cap on Goals**: none for v1. Matches Treason Grants Decision 13.
13. **UI placement**: new "Goals" section on the main column of `GameDetailPage`, immediately below or beside the `TreasonGrantsSection` (`src/pages/GameDetailPage.tsx:116-120`). Visible:
    - For the GM: in `ready`, `playing`, and `archived` (read-only in `archived`).
    - For Players: in `playing` and `archived`. Hidden in `ready` so pre-game prep isn't cluttered (matches Treason Grants' `hidden` gate at `src/pages/GameDetailPage.tsx:1938`).
14. **No standalone "my goals" query**. The list view exposes per-row flags (`isFromMe`, `isToMe`, `canSeeDescription`, `canAssignToPlayer`, `canEdit`, `canDelete`); a "My Goals" filter is a pure client-side filter over the same query. Matches Treason Grants Task 14.

## Implementation Plan

### Phase 1 — Schema

- [ ] Task 1. Add a new `goals` table to `convex/schema.ts` with fields:
    - `gameId: v.id("games")`,
    - `keyword: v.string()`,
    - `keywordLower: v.string()` (normalised form used solely to enforce case-insensitive uniqueness),
    - `description: v.string()`,
    - `type: v.union(v.literal("regular"), v.literal("shared"), v.literal("competitive"))`,
    - `fromPlayerId: v.optional(v.id("players"))`,
    - `toPlayerId: v.optional(v.id("players"))`,
    - `carrot: v.optional(v.number())` (non-negative integer when present),
    - `stick: v.optional(v.number())` (non-positive integer when present),
    - `createdAt: v.number()`,
    - `createdByUserId: v.id("users")`.
    Indexes:
    - `by_game` on `["gameId"]` (per-game listing query),
    - `by_game_keywordLower` on `["gameId", "keywordLower"]` (uniqueness check on create/edit, mirrors `treasonGrants` index at `convex/schema.ts:204`),
    - `by_game_from` on `["gameId", "fromPlayerId"]` (future "my goals as author" filters; index will have `null` slots for goals with no from-player),
    - `by_game_to` on `["gameId", "toPlayerId"]` (future "my goals as target" filters; same `null` caveat).
    Inline comment must reference this plan (`plans/2026-04-27-goals-v2.md`) and rule 24 (server-side authorisation), and explicitly note that **both** `fromPlayerId` and `toPlayerId` are optional (the v2 change vs the original feature request).
    Rationale: identical structural pattern to `treasonGrants` (`convex/schema.ts:189-205`); adds two extra `by_game_<player>` indexes because Goals have *two* player references rather than one, and both are nullable.
- [ ] Task 2. **No `powerLedgerEntries.source` change**. Goals do not write ledger entries in v1 (Decision 7); leave the enum at `convex/schema.ts:114-122` untouched. If a future plan adds automatic carrot/stick payouts, the source enum should be extended with `"goal_carrot"` / `"goal_stick"` literals (or a single `"goal"` source disambiguated by `delta` sign) at that point, not now.

- [ ] Task 9. Add a private helper `assertPlayerInGame(ctx, gameId, playerId)` that loads the player and asserts `player.gameId === gameId`. Throws a clear error otherwise. Used to validate `from_player` and `to_player` references at create and edit time (rule 24 server-side enforcement against cross-game ID forgery). Helper is invoked **only** when the corresponding arg is a non-null id; an `undefined` or `null` arg is short-circuited.
- [ ] Task 10. Add a private helper `assertKeywordUniqueInGame(ctx, gameId, keywordLower, exceptGoalId?)` mirroring `convex/treasonGrants.ts:105-124`.
- [ ] Task 11. Implement `createGoal({ gameId, keyword, description, type, fromPlayerId? (optional id), toPlayerId? (optional id), carrot?, stick? })` mutation:
    1. `assertGoalWritableByGm(ctx, gameId)`.
    2. Validate `keyword`, `description`, `type`, `carrot`, `stick`.
    3. If `fromPlayerId` provided: `assertPlayerInGame(ctx, gameId, fromPlayerId)`.
    4. If `toPlayerId` provided: `assertPlayerInGame`. If `fromPlayerId` is also provided, assert `toPlayerId !== fromPlayerId`.
    5. `assertKeywordUniqueInGame`.
    6. Insert with `createdAt: Date.now()`, `createdByUserId: gmId`. Both `fromPlayerId` and `toPlayerId` may be `undefined` in the inserted row.
    Returns the new `Id<"goals">`.
    Rationale: Decisions 2, 3, 4, 8, 10. Note this is the **v2 change** vs the original feature request: `from_player` is no longer required at create.
- [ ] Task 12. Implement `updateGoal({ goalId, keyword?, description?, type?, fromPlayerId? (nullable id), toPlayerId? (nullable id), carrot? (nullable number), stick? (nullable number) })` mutation (GM-only):
    1. Load goal; `assertGoalWritableByGm(ctx, goal.gameId)`.
    2. For each field, treat as an optional patch. If none provided, no-op.
    3. Validate each provided field using the helpers from Tasks 5–8.
    4. Resolve the **post-patch** values for `fromPlayerId` and `toPlayerId`:
        - `nextFrom` = `args.fromPlayerId === undefined ? goal.fromPlayerId : (args.fromPlayerId === null ? undefined : args.fromPlayerId)`,
        - `nextTo` = `args.toPlayerId === undefined ? goal.toPlayerId : (args.toPlayerId === null ? undefined : args.toPlayerId)`.
    5. If `nextFrom !== undefined`: `assertPlayerInGame(ctx, goal.gameId, nextFrom)`.
    6. If `nextTo !== undefined`: `assertPlayerInGame`, plus assert `nextTo !== nextFrom` (skip the inequality when `nextFrom === undefined`).
    7. **Auto-clear collision invariant**: if the GM sets `nextFrom` to a value equal to the existing `goal.toPlayerId` (and `toPlayerId` was not also being patched in the same call), clear `toPlayerId` in the patch. Symmetric: if the GM sets `nextTo` to the existing `goal.fromPlayerId`, reject with a clear error rather than silently clearing — the GM almost certainly meant to swap, so failing loudly is safer than guessing.
    8. If `keyword` provided and lower-cased changed: `assertKeywordUniqueInGame(..., goal._id)`.
    9. To support clearing `fromPlayerId`, `toPlayerId`, `carrot`, and `stick`, accept the explicit value `null` in args (validators: `v.optional(v.union(v.null(), v.id("players")))` and `v.optional(v.union(v.null(), v.number()))`) and translate `null` to a patch that sets the field to `undefined`. Rationale: Convex `patch` does not directly support deletion; `undefined` removes the field. A `null` arg distinguishes "leave alone" (`undefined` arg) from "clear" (`null` arg). Document this convention in a JSDoc block on the mutation.
    10. `ctx.db.patch(goalId, …)` with the resolved subset.
    Rationale: Decision 8.
- [ ] Task 13. Implement `assignToPlayer({ goalId, toPlayerId })` mutation. This is the **`from_player`-driven** path (Decision 5). Distinct from `updateGoal` because its authorisation rule is bespoke and does *not* apply when `from_player` is unset.
    1. Load goal. Resolve game.
    2. Game must not be `archived` (re-uses the lifecycle gate from Decision 4 — call `requireGame` and assert).
    3. Resolve caller via `requireGameParticipant(ctx, goal.gameId)`. Authorisation:
        - If `role === "gm"`: allowed unconditionally; skip the next checks. (Convenience path; the GM can equivalently use `updateGoal`.)
        - Else (`role === "player"`):
            - Reject if `goal.fromPlayerId === undefined` with `"This Goal has no from-player; only the GM can assign a to-player."` (Decision 5 v2 clause).
            - Reject if caller's `player._id !== goal.fromPlayerId` with `"Only the from-player or the GM can assign a to-player."`.
            - Reject if `goal.toPlayerId !== undefined` with `"This Goal already has a to-player; only the GM can change it."`.
    4. Validate `toPlayerId`: `assertPlayerInGame(ctx, goal.gameId, toPlayerId)`, and assert `toPlayerId !== goal.fromPlayerId` (when `fromPlayerId !== undefined`).
    5. `ctx.db.patch(goalId, { toPlayerId })`.
    Rationale: cleaner authorisation surface than overloading `updateGoal` with conditional caller checks.
- [ ] Task 14. Implement `clearToPlayer({ goalId })` mutation (GM-only): `assertGoalWritableByGm`, then `ctx.db.patch(goalId, { toPlayerId: undefined })`. Idempotent if already cleared. Provides the GM-only inverse to `assignToPlayer`. (Note: there is intentionally no Player-driven `clearToPlayer` — once a `to_player` is set, only the GM can change it, per Decision 5.)
- [ ] Task 15. Implement `deleteGoal({ goalId })` mutation (GM-only): `assertGoalWritableByGm`, then `ctx.db.delete(goalId)`. No ledger work (Decision 7).
- [ ] Task 16. Implement `listGoalsForGame({ gameId })` query returning a redacted, viewer-aware list. Server-side enforces Decision 9.
    1. `requireGameParticipant(ctx, gameId)`; reject non-participants outright.
    2. Read all goals via `by_game` index; sort newest-first by `_creationTime`.
    3. Collect the unique set of player ids referenced by `fromPlayerId` and `toPlayerId` across the result set (skipping `undefined`); bulk-resolve player → user → display name in one pass (mirrors `hydrateOwnerNames` at `convex/treasonGrants.ts:371-386`).
    4. For each goal compute:
        - `canSeeDescription = role === "gm" || (goal.fromPlayerId !== undefined && viewerPlayer?._id === goal.fromPlayerId) || (goal.toPlayerId !== undefined && viewerPlayer?._id === goal.toPlayerId)` — note the explicit `!== undefined` guards so the comparison `viewerPlayer?._id === undefined` (when both viewer and the goal field are unset) cannot accidentally satisfy the predicate,
        - `description: canSeeDescription ? goal.description : null`,
        - `fromPlayerId` (or `null`), `fromDisplayName` (or `null`),
        - `toPlayerId` (or `null`), `toDisplayName` (or `null`),
        - `isFromMe = goal.fromPlayerId !== undefined && viewerPlayer?._id === goal.fromPlayerId`,
        - `isToMe = goal.toPlayerId !== undefined && viewerPlayer?._id === goal.toPlayerId`,
        - `canAssignToPlayer = (role === "gm" || isFromMe) && goal.toPlayerId === undefined && game.state !== "archived"` — note this evaluates to `false` for every Player when `fromPlayerId` is unset (because `isFromMe` requires it), enforcing Decision 5's v2 clause client-side as well as server-side,
        - `canEdit = role === "gm" && game.state !== "archived"`,
        - `canDelete = role === "gm" && game.state !== "archived"`,
        - `keyword`, `type`, `carrot ?? null`, `stick ?? null`, `createdAt`.
    5. Also expose a per-game `players` list (id + displayName) so the client can populate the `from_player` and `to_player` pickers without a second round-trip — same shape as the existing `getGameView` roster (`src/pages/GameDetailPage.tsx:67`).
    6. Return shape: `{ goals: GoalRow[], gameState, eligiblePlayers: { _id, displayName }[] }`. (Renamed from `eligibleToPlayers` in v1 since the same list is now used to populate both pickers.)
    Rationale: encodes server-side rule 24 enforcement (description redaction) and pre-computes capability flags so the client renders trustingly. Matches `listGrantsForGame` (`convex/treasonGrants.ts:309-364`).

## Verification Criteria

- The GM can create a Goal with a 1–40 char keyword, a 0–2000 char description, a `regular | shared | competitive` type, **optional** `from_player` (any Player in this game's roster, or none), **optional** `to_player` (any Player ≠ `from_player`, or none), an optional `carrot` in `[0,1000]`, and an optional `stick` in `[-1000,0]`. Duplicate (case-insensitive) keyword within the same game is rejected.
- Creating a Goal with **no `from_player` and no `to_player`** succeeds and produces a row whose description is visible only to the GM.
- The GM can edit any field of a Goal in `ready` and `playing`, including setting/clearing `from_player` post-creation. `archived` games are read-only with respect to Goals.
- A `from_player` can assign a `to_player` to a Goal whose `to_player` is currently `undefined`, in `ready` or `playing`. They cannot do so once a `to_player` is set, cannot self-assign, and cannot do so in `archived`.
- **A Goal with no `from_player` cannot have its `to_player` set by any Player** — only the GM can, via `updateGoal`. The Player-driven `assignToPlayer` mutation rejects every Player call on such a Goal.
- The GM can clear a Goal's `to_player` at any time outside `archived`. Clearing is idempotent.
- The GM can delete any Goal outside `archived`. Deletion writes no ledger entry and does not change any `players.power`.
- `listGoalsForGame` returns full descriptions to the GM and to the current `from_player`/`to_player` of each Goal; `description: null` to every other participant; **only the GM sees the description on Goals with neither from nor to assigned**; a clear error to non-participants.
- The keyword display formatter returns `"<KEYWORD>"`, `"<KEYWORD> (S)"`, or `"<KEYWORD> (C)"` per Decision 11.
- The carrot/stick formatter returns `"15/-10"`, `"15"`, `"-10"`, or `"---"` per Decision 11; both `0` and "absent" render as `---`.
- The from/to label formatter returns `"Unassigned"` (in muted styling) when the corresponding ref is null.
- After every Goals-touching test scenario, `sum(ledger.delta where playerId = X) === players.power[X]` for every Player. (Goals are a no-op against the ledger.)
- The GoalsSection is hidden for Players in `ready` games; visible for the GM in every state and for Players in `playing` and `archived`.

## Potential Risks and Mitigations

1. **Description leakage via the placeholder**. Rendering different placeholder text for "no description set" vs "redacted because I'm not from/to" vs "no from/to assigned" would let unrelated Players infer the assignment state of the Goal.
   Mitigation: Task 20 uses an identical placeholder regardless. Server returns `description: null` uniformly when the viewer is not authorised.
2. **`from_player` vs `to_player` confusion in the `assignToPlayer` flow**. A Player might assume any Player can claim a Goal as its `to_player` (Treason Grants' "take" semantics), especially on Goals with no `from_player` (where the affordance might look "open").
   Mitigation: Task 13's authorisation explicitly rejects Player calls when `from_player` is unset. The UI affordance (Task 20) only renders `Assign To…` when the server-computed `canAssignToPlayer` is true, which requires `isFromMe || role === "gm"` AND `from_player !== undefined` (for Players). The button copy is `Assign To…`, deliberately distinct from Treason Grants' `Take`.
3. **Cross-game player id forgery**. A Player crafting a request with another game's `playerId` could otherwise be allowed.
   Mitigation: Task 9's `assertPlayerInGame` is invoked on every mutation that accepts a non-null `playerId` arg.
4. **Concurrent keyword uniqueness race**. Two GM browsers creating the same keyword.
   Mitigation: same single-transaction guard via the `by_game_keywordLower` index lookup (Task 10); whichever commits first wins.
5. **Concurrent assignment race**. Two `from_player` clicks racing to set `to_player`.
   Mitigation: Convex single-document transactions; the `goal.toPlayerId === undefined` guard inside `assignToPlayer` ensures only one wins. The losing client surfaces the "already has a to-player" error inline.
6. **Race between GM setting `from_player` and a Player attempting `assignToPlayer`**. With `from_player` now optional, a Goal can flip from "no from" to "has from" mid-session. Since only the GM can change `from_player`, and Players can only `assignToPlayer` when they *are* the `from_player`, the worst case is a Player being newly authorised the moment after they tried (their previous attempt failed; their next attempt succeeds). No corruption is possible. Documenting for completeness.
   Mitigation: rely on Convex single-document transactions; the authorisation check inside `assignToPlayer` reads the live `goal.fromPlayerId` value at execution time.
7. **Carrot/stick formatting drift between server and client**. The server returns raw numbers; only the client formats. If a future feature needs the formatted string server-side (e.g. notifications), duplicating the formatter risks drift.
   Mitigation: keep the formatter pure and exported (`formatCarrotStick`, `formatGoalKeyword`, `formatPlayerLabel`) so it can later be lifted to a shared module without behaviour change. Tests in Task 22 pin the contract.
8. **Players misled by carrot/stick into expecting automatic POWER changes**. Decision 7 makes the values descriptive only.
   Mitigation: render the badge in muted styling (not as a "+15 / -10 awarded" success/failure tag) and document Rule 28 (Task 24) explicitly as "GM applies these via the standard POWER edit flow." A v2 plan may revisit, but no automation in v1.
9. **Lifecycle drift with future game states**. New states could allow Goals mutations unintentionally.
   Mitigation: every Goals mutation routes through `assertGoalWritableByGm` or an explicit `state !== "archived"` check on the loaded game; no `played`-style flag on goals — state is read fresh every mutation. Mirrors Treason Grants Risk 8.
10. **Type field reinterpretation later**. v1 treats `type` as cosmetic (Decision 6). A future rule that ties visibility/permissions to type would require a careful migration to avoid retroactively redacting or exposing existing descriptions.
    Mitigation: Task 24 documents Decision 6 explicitly. Any future plan should call out the migration impact on existing Goals.
11. **Misuse of `from_player`-less Goals as "common pool" goals**. A GM might create Goals with neither from nor to and expect Players to discover them collectively. Such Goals are visible (keyword/type/carrot/stick) to all Players, but the description is GM-only.
    Mitigation: Task 24 documents the visibility rule clearly. If a "common pool" semantic is later wanted (description visible to *all* Players), it is a v2 plan, not a silent reinterpretation.

## Alternative Approaches

1. **Automatic POWER payout on Goal completion**. A new `markGoalCompleted` mutation could write `+carrot` and/or `-stick` ledger entries (with a new `"goal"` source), atomically updating `players.power` (rule 25). Rejected for v1 per Decision 7 — completion semantics (who decides? when? reversible?) are unspecified by the feature request, and inventing them risks misalignment. v2 can add this on top of the v1 schema with no breaking change.
2. **Use the `treasonGrants` table with a `kind` discriminator**. Reuse the existing table by adding `kind: "grant" | "goal"` plus the new fields. Rejected — bloats every Treason Grants query with goal-only fields, complicates indexing, and forces every existing Treason Grants test/UI to reason about two shapes. The marginal duplication of two near-identical modules is the right cost.
3. **Make `from_player` required** (v1's original design). Rejected per the v2 feedback: Goals without an attributed author are useful (e.g. GM-issued objectives, scenario-wide objectives, "anyone who…" prompts). Optional matches the user's intent and reduces friction in early-game prep.
4. **Render Goals in the right rail instead of the main column**. Rejected per Decision 13 — descriptions can be long and benefit from full-width rendering, identical reasoning to Treason Grants Decision 14.
5. **Keyword globally unique (across games)**. Rejected — every other per-game asset (Treason Grants, public bid labels) is per-game; cross-game uniqueness would prevent a GM from re-using a familiar keyword in their next game.
6. **`type` as a free-form string**. Rejected — using a `v.union(v.literal(...))` validator pins the enum at the schema layer and lets the formatter exhaustively switch over the three cases. Adding a fourth type later is a one-line schema diff.
7. **Player-driven self-claim of `from_player`**. A Player could volunteer to be the `from_player` of a Goal with no `from_player`. Rejected for v1 — the original feature request only describes a GM-driven authorship model, and a self-claim flow needs additional rules (can the GM revoke? can the volunteer un-claim? does it require a confirmation from the GM?). v2 can add a `claimFromPlayer` mutation if a stakeholder asks.
8. **Player-driven self-claim of `to_player`**. Symmetrical to Alternative 7, and equally out of scope. Rejected for v1.
