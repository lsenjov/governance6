# Governance — Online Game Application

## Objective

Deliver **Governance**, a multiplayer web app in which users author reusable **Syndicates** (with Minions and drawbacks), run live game sessions as a Game Master (GM), and — as Players — manage POWER, buy Minions, and queue Calls. The app must support live multi-user updates during a `playing` game, enforce role-based permissions (GM vs Player vs author), and persist a full audit trail of POWER changes.

## Stack (locked in)

- **Frontend**: Vite + React + TypeScript. Client-side routing via React Router.
- **Backend, database, real-time**: Convex. Reactive queries drive all multi-user live views (POWER, Call Queue, game state, elapsed time). Mutations are transactional by default, neutralising race-condition risk on POWER edits, Minion buys, and Call replacements.
- **Auth**: Convex Auth with the Password provider (email + password, open self-registration). The user identity surfaced to the app (`userId`) is the Convex Auth users-table id.

## Confirmed Rules

These are the authoritative game rules. Implementation tasks below reference them by number.

1. **User display name** — editable any time on a profile page. **No uniqueness constraint**; duplicates allowed. Trimmed, 1–40 chars.
2. **Syndicate** — has `name`, `leader` (string), `description`, `played` boolean (default `false`), `isShared` boolean (default `false`), and an owner (`ownerId`).
3. **Drawbacks** — each has a `name` and `description`. **0–5 per Syndicate.**
4. **Minions per Syndicate** — up to **8**. Each has a **mandatory** `name`, **optional** `accent` (free text, ≤40 chars), **optional** `description`, and **1–5 skills** (each a single string).
5. **Edit-lock rule** — a Syndicate and its Minions + Drawbacks are editable by the owner **only while `played=false`**. Once `played=true`, the Syndicate (and its children) is frozen permanently but remains selectable in future games.
6. **`isShared` rule** — owner can toggle in either direction **while `played=false`**; it controls whether *other* users can select the Syndicate in their games. It does **not** lock editing. Once `played=true`, `isShared` is frozen at its current value (subject to rule 5).
7. **`played` flag** — purely informational; set automatically to `true` on every selected Syndicate when a game leaves `ready`. It does not force `isShared` and does not bar reuse in future games; it merely freezes content (rule 5).
8. **Edits while selected in a ready game** — allowed (since `played=false`); changes propagate live to the selecting Player via Convex reactivity.
9. **Syndicate deletion** — allowed **only while `played=false`**; on delete, the Syndicate's Drawbacks and Minions are deleted, and the Syndicate is unselected from every `ready`-game Player row that had it selected (`selectedSyndicateId` set to `undefined`). Syndicates with `played=true` cannot be deleted because `playing` and `archived` games still render their content.
10. **Game** — owned by a GM. State enum: `ready` → `playing` → `archived`. Both `ready → archived` and `playing → archived` allowed, **manual GM button only**. No automatic archive.
11. **GM ≠ Player** — the GM of a game **cannot** also be a Player in that same game. The "add Player" picker excludes the GM.
12. **Roster changes** — GM can add/remove Players only while `ready`. While `playing`, removal is **disallowed**; Players remain on the roster until archive. Removing a Player in `ready` deletes their `Player` row (they had zero ledger entries because the game hadn't started).
13. **Syndicate selection** — during `ready`, a Player may select any Syndicate they own, or any Syndicate with `isShared=true` (including their own). Selection is editable until `ready → playing`.
14. **Transition guard** — `ready → playing` is **blocked** if any Player in the roster has no `selectedSyndicateId`. The GM sees an error listing unselected Players. `ready → archived` and `playing → archived` have no such guard.
15. **Lifecycle side-effect** — on `ready → playing`, atomically: (a) stamp `startedAt` with server time; (b) set `played=true` on every distinct Syndicate selected by any Player. All in one Convex transaction.
16. **Elapsed time** — while `playing`, all viewers see a live elapsed-time display derived from `startedAt`, updated client-side at 1 Hz.
17. **POWER** — integer, starts at `0` for every Player. GM may set POWER to any value at any time, with an **optional** reason. POWER can go negative (no floor).
18. **Ledger** — append-only. Every change to POWER writes a ledger entry. Entry fields: `gameId`, `playerId`, `delta` (signed), `reason?`, `source`, `counterpartyPlayerId?`, `createdByUserId`, `createdAt`.
19. **Ledger `source` enum** — `transfer_in`, `transfer_out`, `bank_in`, `bank_out`, `minion_buy`. (No `gm_edit`; GM edits route through bank — see rule 20.)
20. **Transfers and the bank**
    - **Player → Player** (Player-initiated): amount > 0, **reason required**. Writes paired entries: sender `transfer_out` with `counterpartyPlayerId = recipient`; recipient `transfer_in` with `counterpartyPlayerId = sender`.
    - **Player → Bank** (Player-initiated): amount > 0, **reason required**. Writes one entry on the Player's ledger with `source = bank_in` (from the bank's POV: money came in).
    - **GM edits Player POWER** (GM-initiated): any non-zero signed delta. If delta > 0, write one entry on the Player's ledger with `source = bank_out` (bank paid out). If delta < 0, write one entry with `source = bank_in`. Reason is **optional**.
    - **Bank** is an **infinite, GM-controlled, per-game pool**. No balance stored.
21. **Minion buy (in-game)** — per-game state on a join row (`gamePlayerMinions`). Price sequence for the 1st through 8th Minion bought: `[0, 2, 4, 6, 8, 10, 12, 14]`. Buying writes a ledger entry on the buyer's ledger with `source = minion_buy`, `delta = -price`. A Player may only buy Minions that belong to the Syndicate they selected for this game.
22. **Call Queue** — per game.
    - FIFO by `createdAt` ascending.
    - A Player has **at most one** active Call at a time.
    - Adding a new Call while one exists **replaces** the existing Call's `minionId` **in place**, preserving the original `createdAt` (and thus queue position). **Same-minion replace is an idempotent no-op** — `createdAt` and `minionId` remain unchanged.
    - A Player may only add a Call for a Minion they have **bought** in this game.
    - GM may remove any Call; removed Calls are never hard-deleted and appear in a history of the **last 10 removed Calls**.
23. **Ledger visibility**
    - A Player sees their **own** ledger in full (line items with reasons and counterparties).
    - The **GM** sees every Player's full ledger.
    - Other Players see only each Player's current **balance**, never line items.
24. **Authorisation** — enforced server-side in Convex mutations/queries regardless of UI state. Three effective roles per resource: owner (Syndicate author / game GM), participant (Player in a game), viewer (authenticated user).
25. **Balance materialisation** — `players.power` is a **materialised cache** of the ledger sum for the Player's game scope; the ledger is the source of truth. Every mutation that writes a ledger entry also updates `players.power` in the same transaction. A reconciliation test asserts `sum(ledger.delta where playerId = X) == players.power[X]` after every scenario.
26. **Treason Grants** — per-game GM-authored bundles of `(keyword, power, description, ownerPlayerId?)`. Authoritative spec: `plans/2026-04-27-treason-grants-v1.md`. Summary:
    - GM authors and curates; GM cannot **take** a Grant.
    - GM CRUD allowed in `ready` and `playing`; disallowed in `archived`. Take allowed only in `playing`.
    - Players see `keyword`, `power`, and the owner's display name on every Grant. The `description` is visible only to the GM and to the owning Player; redacted (identical placeholder) for unowned and not-yours-owned cases alike.
    - Take pays the listed POWER to the taker via a single ledger entry (`source = "treason_grant"`, `delta = +power`) in the same transaction that sets `ownerPlayerId` and patches `players.power` (Rule 25).
    - Once a Grant is owned, the GM may edit `keyword`/`description` but **not `power`**. Delete is allowed in any non-archived state and does NOT reverse POWER. The GM may **clear** the owner (with confirmation); clearing does NOT reverse POWER and re-opens the Grant for any Player to take again, who then receives the listed POWER again.
    - Keyword is unique within a game (case-insensitive); 1–40 chars. POWER is a positive integer 1–1000. Description is 0–2000 chars.
    - Rule 19's `source` enum is extended with `"treason_grant"`.

## Verification Criteria

- A new user can register, set a (non-unique) display name, create a Syndicate with 0–5 drawbacks and up to 8 Minions (each with 1–5 skills, optional `accent` ≤40 chars), and toggle `isShared` on and off while `played=false`.
- Every mutation that edits a Syndicate, Drawback, or Minion fails with an authorisation error when the parent Syndicate has `played=true`. `isShared` alone never blocks edits.
- Deleting a Syndicate with `played=false` succeeds, removes its Drawbacks and Minions, and clears the selection from every `ready`-game Player who had it selected. Deleting a Syndicate with `played=true` fails.
- A GM can create a game, add/remove Players while `ready`, and Players can select either an owned Syndicate or any `isShared` Syndicate. A GM cannot be added as a Player to their own game; the same user cannot appear twice in a game's roster.
- `ready → playing` is rejected when any Player has no Syndicate selection; the error lists the offending users. When all Players are selected, the transition atomically stamps `startedAt` and flips `played=true` on every distinct selected Syndicate; any failure rolls back.
- Roster changes are disallowed while `playing`. `ready → archived` and `playing → archived` are GM-only.
- All clients viewing a `playing` game see elapsed time within one second of each other, updating continuously.
- POWER starts at `0` for every Player. GM edits (positive → `bank_out`, negative → `bank_in`), Player→Player transfers, Player→Bank transfers, and Minion buys each produce correct ledger entries. The ledger exposes no update/delete endpoints. The `gm_edit` source does not appear in the schema.
- Transfers (Player→Player and Player→Bank) reject empty/whitespace reasons and non-positive amounts. GM POWER edits accept optional reasons and reject zero delta.
- POWER can go negative (no floor check).
- `players.power == sum(ledger.delta for that player)` after every mutation in the reconciliation test.
- Buying the 1st–8th Minion for a Player in a Game costs exactly `0, 2, 4, 6, 8, 10, 12, 14` POWER respectively; each purchase writes a matching `minion_buy` ledger entry; the 9th buy is rejected.
- A Player cannot hold more than one active Call. Replacing with a different Minion updates the existing Call's `minionId` in place, preserving `createdAt` and document id. Replacing with the same Minion is a no-op.
- GM-removed Calls appear in the removed-history view, capped at the 10 most recent, ordered by `removedAt` descending.
- Ledger visibility: Player A sees own full ledger and sees Player B's balance only; GM sees every ledger in full.
- Authorisation tests prove: non-GMs cannot transition state, edit POWER, or remove Calls; non-authors cannot edit Syndicates; non-Players cannot buy Minions, add Calls, or transfer POWER; users outside a game cannot read its private data.
- Display name (not email or id) is the rendered identifier everywhere a user is surfaced.

## Potential Risks and Mitigations

1. **Race conditions on POWER, Minion buys, and Call replacement.**
   Mitigation: every mutation is a single Convex transaction reading and writing all affected documents; no multi-step non-transactional sequences.
2. **Convex Auth is still labelled beta.**
   Mitigation: auth calls isolated behind `convex/lib/auth.ts`; swap to Clerk later is mechanical if needed.
3. **Replace-in-place Call semantics (rule 22) are easy to get wrong by re-inserting.**
   Mitigation: dedicated test (Task 47); explicit code comment in the mutation linking to rule 22.
4. **Edit-lock drift**: tempting to lock on `isShared`; the rules reject that.
   Mitigation: single `assertSyndicateEditable(ctx, syndicateId)` helper asserts on `played` only (Task 9); covered by tests.
5. **Ledger visibility leak.**
   Mitigation: never expose raw `powerLedgerEntries` in a query; only the three scoped queries from Task 28.
6. **Live updates subtly missing** because a component fetched through a non-reactive path.
   Mitigation: lint rule or code review checklist enforcing `useQuery` for all game-page data (Task 40); Playwright asserts cross-context updates (Task 53).
7. **Uniqueness of `(gameId, userId)` on players.**
   Mitigation: compound index + explicit guard in `addPlayer` (Task 18); explicit note in rule 16 that Convex has no schema-level unique constraints.
8. **GM-as-Player** slipping in via a direct `addPlayer` call.
   Mitigation: server-side check in `addPlayer` rejecting the GM (Task 18); covered by Task 46.
9. **Cascade-delete side effects** when a shared Syndicate is deleted.
   Mitigation: rule 9 + Task 10 make the cascade explicit and test-covered (Task 51); `played=true` deletes blocked entirely.
10. **Ledger / `players.power` drift**.
    Mitigation: both written in every mutation's single transaction; reconciliation test (Task 52).
11. **N+1 queries** on game pages with many Players, Minions, Calls, ledger rows.
    Mitigation: bulk queries (`getPlayerBalances`, `activeCalls` join-preloads names); paginate ledger views.
12. **Convex index misuse** (no filter predicates).
    Mitigation: `calls.isActive` boolean field kept in sync with `removedAt` (rule 22; Task 34).

## Alternative Approaches (historical — stack is locked)

These were considered and rejected in favour of Convex + Vite + React:

1. **Phoenix LiveView** — excellent real-time, but not TypeScript.
2. **Rails + Hotwire** — mature, but heavier infra and no first-party TS.
3. **Next.js + Convex** — viable, but SSR is unnecessary for an auth-gated game app and adds deploy complexity over a static Vite SPA.
4. **REST + polling** — simpler, but loses the live-updating Call Queue and elapsed-time UX that Convex gives almost for free.

## Domain Specification (preserved from `plans/init.md`)

Retained verbatim for traceability. The confirmed rules above take precedence where they refine or clarify this text.

- Each user has a display name, which can be changed at any time from a profile page.
- A user can create Syndicates. Each Syndicate has a name, leader and description. Each Syndicate has a `played` boolean, default `false`. Each Syndicate has a number of drawbacks (name + description). Each Syndicate has an `is-shared` boolean, default `false`; if true, users cannot modify details of the Syndicate or Minions.
- Each Syndicate has up to 8 Minions. Each Minion has a mandatory name, optional accent, optional description, and 1–5 skills (each a single string).
- Users can create a game; the owner is the GM. Games have state (`ready`, `playing`, `archived`); all users see status, only the GM can change it.
- Games have a start time, nil by default. The game tracks when it moves to `playing` and displays elapsed time to all users while `playing`. While `ready`, the GM can add/remove Players. While `ready`, a Player can select any own Syndicate, or any Syndicate with `is-shared=true`. When the game leaves `ready`, all selected Syndicates have `played` set to `true`.
- Each Player has integer POWER (GM-editable). Each Player has a ledger of POWER income and expenditures with an optional reason. POWER can go negative. A Player can send a positive amount of POWER to any other Player or the bank, with a reason.
- In each game, each Player sees their own Minions and whether they've been bought; they can buy Minions. First Minion is free; subsequent prices are 2/4/6/8/10/12/14.
- Each game has a Call Queue. A Player can add a bought Minion; only one Call per Player (new replaces old). GM can remove calls. A removed-calls history shows the last 10.
