# Dice rolls (skill + chaos) on top-of-queue calls

## Objective

Introduce a GM-only dice-roll system that fires automatically whenever a
Call reaches the head of the FIFO queue (Rule 22, `convex/calls.ts:11-19`).
Each event produces at minimum two six-sided rolls:

- **Skill roll** — compared against the called Minion's skill count
  (`minions.skills.length`). A roll **≤** that count is rendered as a
  **failure**; a roll **>** that count is rendered as a **success**.
- **Chaos roll** — a plain d6 with no pass/fail interpretation.

The rolls are visible **only to the GM**, regardless of where they appear
(the right-rail Call Queue, the main-column Current Call section, or
inline next to a Note). The data model must accommodate "more rolls
added conditionally in the future" without further schema churn.

When a Note is created against the Minion that is currently at the top
of the queue, the active roll set is **frozen onto the Note**, so the
GM can later read the Notes log and see which rolls were live at the
moment the Note was made — even after the call has been removed and
the rolls would otherwise be gone.

Visually, dice render as brutalist square cells: hard 2px black border,
zero radius, big mono numerals (no pip dots, no skeuomorphic die faces).
Failure is signalled by riot-red treatment; success uses the existing
mint accent strip; chaos is presented neutrally in white. The look
continues the system already shipped per `THEME.md:62-91`.

## Key findings & rationale

1. **Roll generation is a side-effect of "becoming the head."** The
   only deterministic way to detect a "new head" is at the moment a
   mutation changes the queue: `addOrReplaceCall` (adding to an empty
   queue, or changing the minion of the existing head call) and
   `removeCall` (the next-oldest call inherits the head slot). All
   roll generation belongs in those two mutations via a shared helper.
   This keeps queries pure and live-subscribable.

2. **Replace-in-place needs a new roll set.** `addOrReplaceCall` keeps
   the same `_id` and `createdAt` when the caller swaps minions
   (`convex/calls.ts:52-60`), but the _skill count_ is derived from
   the minion. Without a re-roll the skill result would be stale. We
   therefore generate a fresh roll set whenever the head call's
   `minionId` changes. Same-minion replace stays the documented no-op.

3. **Roll sets must be immutable, append-only, and addressable by id.**
   This satisfies three constraints simultaneously:
   - notes need to "freeze" the roll set live at note-creation time;
   - replace-in-place must keep older roll sets intact (a Note made
     before the swap still references the pre-swap rolls);
   - "more rolls added conditionally in the future" reduces to
     "another optional field or another `extras` array entry on the
     same row" rather than a schema rewrite.

4. **One row per roll set, not one row per individual die.** Every
   "becoming the head" event always emits the skill+chaos pair
   atomically; future conditional dice will be authored alongside
   them. A single `callRollSets` row captures the full bundle as a
   transactional unit. Future conditional rolls go into an `extras`
   array of `{ kind, value, label?, result? }` objects on the same
   row — extensible without migration.

5. **GM-only at the data boundary, not just the UI.** Rule 24 demands
   server-side enforcement. Roll data must therefore be stripped from
   any response served to a non-GM viewer — even when the underlying
   row exists. This is enforced inside the existing query handlers
   (`activeCalls`, `listNotesForTarget`, etc.), not the React layer.

6. **Notes capture the roll-set id, not a snapshot.** Roll-set rows
   are immutable, so a foreign key is sufficient and avoids
   duplicating data. Players never see the field — the API filters it
   out for non-GM viewers.

7. **Brutalist dice = numerals in a hard-bordered cell.** The theme
   forbids pip ornament, rounded corners, and gradient shadows
   (`THEME.md:62-91`). The two existing visual primitives that map
   to "two-state success/failure" are the riot-red top-border on
   `.card.drawback` (`src/index.css:986-994`) and the mint accent
   strip used on links/buttons. Reusing them keeps the dice in-style
   and avoids new CSS tokens.

## Implementation Plan

### Backend: schema

- [ ] Task 1. Add a `callRollSets` table to `convex/schema.ts`. Each
      row represents one "becoming-the-head" event for a specific call
      and is immutable once written. Fields: - `gameId: v.id("games")` — for per-game scoping and indexes. - `callId: v.id("calls")` — owning call. - `minionId: v.id("minions")` — snapshot of the called Minion at
      roll time (so a later replace-in-place doesn't invalidate
      historical roll sets attached to old Notes). - `skillRoll: v.number()` — integer 1–6. - `skillCount: v.number()` — non-negative integer, snapshot of
      `minions.skills.length` at roll time (the threshold). - `skillResult: v.union(v.literal("success"), v.literal("failure"))`
      — derived once from `skillRoll <= skillCount` (failure) vs
      `skillRoll > skillCount` (success); persisted so display logic
      never re-derives it. - `chaosRoll: v.number()` — integer 1–6. - `extras: v.array(v.object({ kind: v.string(), value: v.number(),
    label: v.optional(v.string()), result:
    v.optional(v.union(v.literal("success"), v.literal("failure"))) }))`
      — empty for v1; reserved for future conditional rolls. - `createdAt: v.number()`. - `createdReason: v.union(v.literal("became_head"),
    v.literal("minion_replaced"))` — audit aid; distinguishes the
      two trigger paths in Tasks 4–6.
      Indexes: - `by_call_created` on `["callId", "createdAt"]` — used to fetch
      the most-recent roll set for a given call in O(1). - `by_game_call` on `["gameId", "callId"]` — supports per-game
      listings and bulk reads in `activeCalls`.

- [ ] Task 2. Extend the `notes` table at `convex/schema.ts:159-182`
      with an optional `attachedRollSetId: v.optional(v.id("callRollSets"))`.
      Optional because (a) Notes against `game` and `syndicate` targets
      never carry rolls, (b) Notes against a Minion that is **not**
      currently the head of the queue do not carry rolls, and (c)
      historical Notes pre-dating this feature have no roll set. No
      new index is required — Notes are already queried by their
      target indexes, and the field is read-after-fetch.

### Backend: roll generation helper

- [ ] Task 3. Add a private helper `generateRollSetForCall` in a new
      module `convex/lib/rolls.ts` (mutation-context only, since it
      uses `Math.random()`). Signature conceptually:
      `(ctx: MutationCtx, args: { callId, reason: "became_head" |
  "minion_replaced" }) => Promise<Id<"callRollSets">>`. The helper: 1. Loads the call, throws if missing or `isActive === false`
      (defensive — the helper must never run for an inactive call). 2. Loads the minion via `call.minionId`. If missing (a deletion
      race), returns without inserting and logs a console warning
      — the caller is in a "queue is broken" state anyway. 3. Computes `skillRoll = 1 + Math.floor(Math.random() * 6)` and
      `chaosRoll = 1 + Math.floor(Math.random() * 6)`. 4. Computes `skillCount = minion.skills.length` and
      `skillResult` per Task 1. 5. Inserts a `callRollSets` row with `gameId = call.gameId`,
      `extras: []`, `createdAt: Date.now()`, `createdReason: reason`,
      and returns the new id.
      Centralising this logic guarantees the same code path is used
      from both mutation entry points and from any future conditional
      roll add-on.

### Backend: trigger sites

- [ ] Task 4. In `addOrReplaceCall` (`convex/calls.ts:22-70`), add
      roll generation at the two sites that mutate the head: - **Empty-queue insert** (`convex/calls.ts:62-68`): after the
      `ctx.db.insert("calls", …)` returns, immediately call
      `generateRollSetForCall(ctx, { callId, reason: "became_head"
    })`. The new call is by definition the head because the queue
      was empty at the start of the transaction (the existing
      check at `convex/calls.ts:44-50` already enforces "no other
      active call for this player," and a queue-wide head check is
      unnecessary because the new call's `createdAt` is by
      definition the newest only when no others exist).
      Important nuance: Players other than the caller may have
      active calls older than this one. In that case the caller's
      new call is **not** the head and rolls must NOT be generated.
      The helper should therefore explicitly query the
      `by_game_active_time` head and skip generation if the new
      call's `_id` is not the current head. - **Replace-in-place** (`convex/calls.ts:52-60`): when
      `existing.minionId !== args.minionId`, after the patch, check
      whether `existing._id` is the current head via the
      `by_game_active_time` index. If it is, generate a new roll
      set with `reason: "minion_replaced"`. Otherwise no rolls
      (the call is mid-queue; rolls will be generated later when it
      becomes the head — see Task 5).
      Same-minion replace remains the documented no-op
      (`convex/calls.ts:53-56`).

- [ ] Task 5. In `removeCall` (`convex/calls.ts:76-92`), after the
      patch that soft-deletes the head call, look up the new head via
      `by_game_active_time` (oldest active in the same game). If a
      next call exists, generate a roll set for it with
      `reason: "became_head"`. If the queue is now empty, no-op.
      Note: only the GM may invoke this mutation, but the helper does
      not depend on caller role — it's the queue state that drives
      the roll, not who removed the call.

- [ ] Task 6. Edge case: if the GM removes a **mid-queue** call (not
      the head), no head change occurs and no rolls fire. Verify this
      is the natural behaviour of Task 5's "look up the new head"
      step — the head is unchanged, so the helper is called for the
      same call that already has a roll set. To avoid generating a
      duplicate roll set in that case, Task 5 must compare the
      removed call's `_id` to the pre-patch head's `_id` and only run
      generation when the removed call **was** the head. Document
      this guard explicitly in code comments.

## Verification Criteria

- A GM playing through a queue of three calls sees a fresh skill+chaos
  pair appear on each of the three calls **in turn** as they reach
  the head, and the rolls disappear from the rail when the GM removes
  the call.
- The skill roll shows as **failure** iff `skillRoll <= skillCount`,
  and as **success** otherwise; the visual treatment matches Task 12.
- A GM who replaces the head call's minion sees an entirely new pair
  of rolls, with `skillCount` reflecting the new minion. Replacing
  with the _same_ minion is a no-op; rolls do not change.
- A GM who removes a _mid-queue_ call sees the head's rolls unchanged
  (no spurious re-roll).
- A Player viewing the same game sees no dice cells anywhere — neither
  in the rail, the bottom sheet, the Current Call section (which they
  never see anyway), nor inline on Notes. The `activeCalls` and
  `listNotesForTarget` payloads they receive contain no `rolls` /
  `attachedRolls` / `attachedRollSetId` fields whatsoever.
- A Player notes the head Minion of the queue. The Note appears
  immediately in the popover and Current Call section; the GM viewing
  that same Note sees the dice that were live at the moment the Note
  was authored. After the Player or GM advances the queue (causing a
  fresh roll set), the older Note **still** displays its original
  rolls (immutable history).
- A non-participant calling `activeCalls`,
  `getCurrentCallDetails`, `listNotesForTarget`, or `createNote`
  receives the existing "not a participant" / "not the GM" errors.
  None of the new code paths leak rolls.
- All dice cells render with hard 2px black borders, no border
  radius, no blurred shadows, mono numerals with tabular-nums; the
  failure variant uses the riot-red top rule and the success variant
  uses the mint accent strip — matching `THEME.md:62-91` and the
  verification checklist at `THEME.md:182-198`.
- All new and existing backend tests pass under `npm test` /
  `vitest`, and `npx convex codegen` (or equivalent) succeeds with
  the new schema.

## Potential Risks and Mitigations

1. **Race between queue mutation and read.** A subscriber querying
   `activeCalls` between the `ctx.db.insert("calls", …)` and the
   `generateRollSetForCall` call could briefly see `rolls === null`.
   Mitigation: both operations live in the same mutation transaction
   in Convex, so external readers will only see the post-commit state
   in which both rows exist. The `null` branch of `RollSetDisplay`
   (Task 12) exists purely as defence-in-depth for replay/error paths.

2. **Replace-in-place ambiguity.** Reasonable readers may disagree on
   whether a same-call minion swap counts as "becoming the top."
   Mitigation: Task 4 documents the chosen interpretation
   ("minion change → re-roll") and the `createdReason` field
   (`became_head` vs `minion_replaced`) records which path produced
   each row, supporting future audit and policy reversal.

3. **Wire-format leakage.** A naive `if (isGm) item.rolls = …` left
   the field on the response object as `undefined`, which JSON-omits
   but Convex value-encodes — Players would still see the _key_
   absent in JSON but present in the validator. Mitigation: build
   the response object via two distinct shapes (Player branch never
   constructs the field at all). Add the explicit `hasOwnProperty`
   assertion in Task 16's tests to catch regressions.

4. **Test flakiness from `Math.random()`.** Asserting exact roll
   values is impossible. Mitigation: tests assert _invariants_
   (range, count, derived `skillResult`, schema fields, presence of
   the row), not specific outcomes; the property-style "loop and
   verify the rule holds for every run" pattern in Task 16 catches
   skew without coupling to a seed.

5. **Schema migration on existing notes.** `attachedRollSetId` is
   optional, so old notes remain valid. Mitigation: explicit
   `v.optional(...)` validator and no backfill required. Confirm by
   running tests against the existing fixtures unchanged.

6. **Read-budget growth in `activeCalls`.** Each call now triggers a
   roll-set lookup. Mitigation: Task 8's "single bulk read into a
   Map" approach keeps reads at O(active calls + active rolls in the
   game), which is bounded by the per-player at-most-one-active-call
   rule (`convex/calls.ts:44-50`).

7. **Brutalist constraints regressed.** Adding a new visual primitive
   risks introducing `border-radius` or blurred shadows.
   Mitigation: Task 12 names the existing tokens to reuse and forbids
   new design tokens; Task 19's verification step explicitly walks
   the `THEME.md:182-198` checklist on the new component.

8. **Future conditional rolls colliding with `extras`.** A future
   feature might want richer per-roll data (e.g. context, links).
   Mitigation: `extras` is an array of objects whose only required
   fields are `kind` and `value`; everything else is optional and
   adding new optional keys is a non-breaking schema change in
   Convex.

## Alternative Approaches

1. **Compute rolls on demand from a deterministic seed.** Rather than
   storing roll-set rows, derive rolls from a hash of `(callId,
generation, gameSecret)`. Trade-off: still need a row to record
   "generation" per top-event and to attach to Notes, so the storage
   savings are nil; deterministic seeds also bake replay-debuggability
   into a security-sensitive surface. Rejected.

2. **One row per individual die.** Use a `callRolls` table with one
   row per die kind. Trade-off: simpler in the abstract, but every
   read needs to assemble a "set" by scanning multiple rows ordered
   by a synthetic `setId`, which complicates Note attachment (the
   Note would need either an array of ids or a join through a
   `callRollSets` parent that we're trying to avoid in the first
   place). Rejected — the parent row is unavoidable.

3. **Snapshot rolls onto the Note instead of FK.** Store the literal
   `skillRoll`/`chaosRoll` on the note row. Trade-off: duplicates
   data, complicates schema changes when `extras` grows, and makes
   it harder to surface the same rolls in multiple UI places (Note
   list and Current Call header) without divergence. Rejected.

4. **Generate rolls from a query (lazy).** Have `getCurrentCallDetails`
   roll dice when no row exists. Trade-off: queries in Convex are
   deterministic and cannot use `Math.random()` reliably; would also
   create a roll on every cold subscription. Rejected — generation
   must remain a mutation-side effect.

5. **Surface rolls only in the Current Call section, not the rail.**
   Simpler UI. Trade-off: the user explicitly asked for rolls on
   "the call," and the rail is the canonical call display in the
   mobile drawer where the GM doesn't have the main column visible.
   Rejected — both surfaces matter.

6. **Show rolls to Players too.** Trade-off: directly contradicts
   the user's "Only the GM can see dice rolls, at any time, no
   matter where they are in the game" requirement. Rejected.
