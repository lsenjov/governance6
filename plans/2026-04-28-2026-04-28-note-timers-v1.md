# Note Timers (GM-only)

> **Superseded scope (2026-04-28):** the original "timer ⇒ pinned
> roll set" invariant asserted below is relaxed by
> `plans/2026-04-28-gm-todo-drawer-v1.md` (Task 0b). Post that plan,
> the GM may attach a timer to ANY note kind they author —
> game-target, syndicate-target, or minion-target (head call or not).
> The GM-only wire-format treatment, the preset durations, and the
> Done / Due-manual cycle are all unchanged. Read this plan for the
> cell UX and persistence model; cross-reference the GM Todo Drawer
> plan for the broadened create-time gate.

## Objective

Add a GM-only "clock" affordance to notes that already attach a frozen
roll set (i.e. minion-target notes authored while that minion is the
head of the call queue). The GM picks one of five preset durations
(2 / 5 / 10 / 15 / 30 minutes) at note-creation time instead of
pressing the standard "Post" button; the chosen timer becomes a fourth
brutalist square cell rendered alongside Skill, Chaos, and any
drawback dice on the posted note. The GM can later cycle the cell
through "Done" and a manual "Due" via clicks. Players never see the
clock.

## Background — what the spec maps to

- "Notes with skill checks" = minion-target notes whose `attachedRollSetId` is
  set. Only the GM sees those rolls today (`convex/notes.ts:253-280`,
  `src/components/NoteIcon.tsx:30-39`). The clock inherits the same
  GM-only wire-format treatment.
- "Mimicking the same style as skill checks" = reuse the existing
  `.roll-cell` markup and CSS variants (`src/index.css:1018-1123`,
  `src/components/RollSetDisplay.tsx`). No new design tokens.
- "Same as a failed roll" = `.roll-cell.failure` (riot-red 6px top
  rule). "Done" reuses `.roll-cell.success` (4px mint inset bottom
  strip). Neutral = unmodified `.roll-cell`.

## Design — the four UI states

| State key      | Caption | Body            | Badge | Cell variant   |
| -------------- | ------- | --------------- | ----- | -------------- |
| **A** ticking, future | `CLOCK` | `MM:SS`         | none  | neutral        |
| **B** ticking, past   | `CLOCK` | `-MM:SS` (cap −99:59) | `DUE`   | failure        |
| **C** done            | `CLOCK` | (no value cell) | `DONE`  | success        |
| **D** due manual      | `CLOCK` | `!`             | `DUE`   | failure        |

States A and B share the same persisted record (`kind: "ticking"` with
a `dueAt`); the visual flip is purely a client-side comparison of
`Date.now()` vs `dueAt`. There is no persisted "expired" state.

Click semantics (GM only):

- A → C
- B → C
- C → D
- D → C

That gives Done ↔ DueManual as a binary toggle once the timer has been
clicked at least once, exactly per the spec.

## Persistence model

A new optional sub-object on the `notes` row:

```
timer?:
  | { kind: "ticking", dueAt: number }   // ms since epoch
  | { kind: "done" }
  | { kind: "due_manual" }
```

Why `dueAt` (single absolute timestamp) instead of
`startedAt + durationMs`:

- The UI only ever needs the deadline; the duration the GM clicked is
  never read again.
- One field, not two — fewer invariants to maintain.
- States A and B fall out of a single comparison without a separate
  flag.

Mutation-time guarantees:

- `kind: "ticking"` MUST carry a finite `dueAt` (positive integer).
- `kind: "done"` and `kind: "due_manual"` MUST NOT carry `dueAt`
  (Convex value validators enforce this via discriminated union
  literals).
- Once a note has `timer.kind === "done"` or `"due_manual"`, the
  toggle mutation cannot move it back to `"ticking"` — the original
  countdown is gone for good. (Spec implies this: re-clicking only
  flips between Done and Due-manual.)

## Implementation Plan

### Schema + server (Convex)

- [ ] **Task 1.** Extend the `notes` table schema (`convex/schema.ts:272-296`) with an optional `timer` field typed as a discriminated union (`v.union(v.object({kind: v.literal("ticking"), dueAt: v.number()}), v.object({kind: v.literal("done")}), v.object({kind: v.literal("due_manual")}))`). The field is omitted on legacy rows. Rationale: native Convex validators give us free shape enforcement on every write.

- [ ] **Task 2.** Define a single source-of-truth list of allowed durations as a const (e.g. `TIMER_PRESET_MINUTES = [2, 5, 10, 15, 30] as const`) inside `convex/notes.ts`. Re-export so the client picks up the same list and stays in sync. Rationale: the buttons must match what the server validates.

- [ ] **Task 3.** In `createNote` (`convex/notes.ts:55-159`) accept an optional `timerMinutes` arg. When present:
   - reject unless the caller is the GM of `args.gameId` (use `requireGameGm` semantics; the participant payload already exposes role).
   - reject unless the resulting note will have `attachedRollSetId` set (i.e. minion-target + minion is currently head). If the caller asks for a timer on any other target, throw a clear error.
   - reject unless the value is one of the preset minutes.
   - on success, write `timer: { kind: "ticking", dueAt: Date.now() + minutes * 60_000 }`.
   Rationale: server-side gate enforces every part of the "GM only, only with skill checks" rule (Rule 24 of the project: server-side authorisation regardless of UI).

- [ ] **Task 4.** Add a new mutation `cycleNoteTimer` in `convex/notes.ts` taking `{ noteId }` only (no caller-supplied next state). The mutation:
   - looks up the note; throws `Note not found` if missing,
   - calls `requireGameGm` against the note's `gameId`,
   - throws if `note.timer` is absent (no clock to cycle),
   - applies the state machine: `ticking → done`, `done → due_manual`, `due_manual → done`,
   - writes the new sub-object via `ctx.db.patch`.
   Rationale: the verb-free single-mutation design matches the spec's "click to cycle" UX, leaves no client-side state authority, and prevents an attacker forging a forward-running timer (no `ticking` is ever reachable post-cycle).

- [ ] **Task 5.** Update `listNotesForTarget` (`convex/notes.ts:190-304`) so the projected `NoteListItem` carries `timer` exactly when:
   - the viewer is the GM, AND
   - the row has a `timer` field.
   Strip the field for non-GM payloads in the same place `attachedRollSetId` is filtered (the existing `role === "gm"` branch around `convex/notes.ts:257-280`). Mirror the omit-vs-null discipline used for `attachedRolls` so the wire format stays tight.

- [ ] **Task 6.** Update the exported `NoteListItem` type in `convex/notes.ts:175-188` AND the duplicate in `src/components/NoteIcon.tsx:21-39` to add `timer?: TimerState` (where `TimerState` is the same discriminated union). Re-export the type from one place and import it on both sides if practical, to prevent drift.

- [ ] **Task 7.** Server tests in `convex/notes.test.ts`:
   - createNote with `timerMinutes` rejects Players,
   - createNote with `timerMinutes` rejects GM on non-minion targets,
   - createNote with `timerMinutes` rejects GM on a minion that isn't the head,
   - createNote with an unsupported preset (e.g. 7) rejects,
   - createNote with a valid preset writes `kind: "ticking"` and a `dueAt` ≈ `now + minutes*60_000` (allow a small skew),
   - cycleNoteTimer rejects Players,
   - cycleNoteTimer rejects when no timer exists,
   - cycleNoteTimer cycles ticking → done → due_manual → done,
   - cycleNoteTimer never produces `ticking` after first cycle (regression guard),
   - cycleNoteTimer leaves body / visibility / target / attachedRollSetId untouched (immutability invariant for non-timer fields).
   - listNotesForTarget strips `timer` for Players and includes it for the GM.

### Client (React)

- [ ] **Task 8.** Add a `TimerCell` component in a new file (e.g. `src/components/NoteTimerCell.tsx`) that renders a single `.roll-cell`-class element matching the brutalist primitives. Props: `{ timer: TimerState; size?: "sm" | "md"; onCycle?: () => void; readOnly?: boolean }`. Internally:

## Verification Criteria

- A GM creates a minion-target note while a head call is live; five duration buttons render next to "Post"; clicking `5` posts the note and the popover shows a clock cell counting down `04:59`, `04:58`, …
- The same GM creates a syndicate-target note while a head call is live; no duration buttons appear (target is not minion).
- The same GM creates a minion-target note while NO call is at the head; no duration buttons appear.
- A Player has the popover open while the GM creates a timer-bearing note; the Player's notes list re-renders with NO clock cell (server stripped the field).
- The clock cell crosses zero: it switches from neutral `MM:SS` to failure-styled `-MM:SS` with a `DUE` badge, no page reload required, all driven by client tick alone.
- The clock cell on a long-running expired note caps at `-99:59` and stays there.
- GM clicks the clock cell while ticking → cell flips to success-styled, `DONE` badge, no value, and `setInterval` is cleared (no further re-renders).
- GM clicks the `DONE` cell → flips to failure-styled `!` with `DUE` badge.
- GM clicks the `!` cell → flips back to `DONE`.
- A Player viewing the same note never sees any clock-related state changes.
- The note's body, visibility, and attached roll set are byte-identical before and after every cycle (server test).
- No `console.error`/`console.warn` from React tick re-renders.

## Potential Risks and Mitigations

1. **Per-second re-render of the whole popover.**
   Mitigation: localise the `setInterval` inside `<TimerCell>` only; the parent does not depend on `Date.now()`. The cell's `useEffect` clears the interval immediately on transition out of `kind: "ticking"`.

2. **Server-side enforcement of "skill-check eligibility" diverges from the client gate.**
   Mitigation: both gates derive from the same predicate ("minion is the head of the active queue"); centralise it in a tiny helper inside `convex/notes.ts` (or `convex/lib/calls.ts`) and call it from both `createNote`'s server validator AND the popover's eligibility query. One source of truth.

3. **Discriminated-union value validators in Convex.**
   The schema must reject `{ kind: "done", dueAt: 123 }`. Mitigation: model with `v.union` of three distinct `v.object` shapes — Convex rejects unknown keys per object — rather than a single object with optional `dueAt`. Add a regression test that a doctored mutation cannot smuggle a `dueAt` into a non-ticking shape.

4. **Clock skew between GM's browser and the server `Date.now()`.**
   The server stamps `dueAt`; the client compares against its own clock. A skew of >5s could make the cell "due" early/late.
   Mitigation: accept this as a known limitation — the timer is an in-table game prop, not a financial deadline. Document the client-clock dependency in the file-top comment so future contributors don't try to fix it with a heartbeat.

5. **Once cycled, ticking is unrecoverable.**
   Spec-intentional, but a GM who fat-fingers Done on a still-ticking timer cannot recover the original deadline.
   Mitigation: confirmation dialog is overkill for a GM-only tool. Document the no-undo behaviour in the cell's `aria-label` and a tooltip on hover (e.g. `title="Mark done (cannot be undone to ticking)"`).

6. **Duplicate immutability comment drift.**
   Notes' top-of-file comment currently says "IMMUTABLE once created". Failing to update it leads to future misreads.
   Mitigation: Task 17 amends the comment in the same diff that introduces the timer mutation; CI does not enforce this so reviewers must check.

7. **Drawback dice extras already crowd the row.**
   On a syndicate with 3+ rolled drawbacks the clock cell becomes the 6th cell and may wrap on narrow viewports.
   Mitigation: `.roll-set` already wraps via `flex-wrap: wrap` (`src/index.css:1011-1016`); no extra work, but the cell is added at the END so wrapping degrades gracefully.

## Alternative Approaches

1. **Server-pushed expiry events instead of client tick.** A scheduled Convex function fires when `dueAt` is reached and patches the note to `{ kind: "expired" }`. Trade-off: removes client-clock skew, but introduces a fifth state and a scheduler dependency for a purely cosmetic transition. Rejected.

2. **Store `startedAt + durationMs`, derive `dueAt` on read.** Was the initial draft (Q7). Rejected: two fields where one suffices, and the duration is never re-read.

3. **Single mutation `setNoteTimerState({ noteId, next })` taking the next state literal.** More flexible than `cycleNoteTimer`, allows direct UI shortcuts (e.g. a future "Reset to Done" affordance from any state). Trade-off: lets a buggy or malicious client jump from `done` back to `ticking` with a forged `dueAt`. Reject; keep the cycle-only mutation.

4. **Render the clock as a separate row beneath the dice instead of inline.** Simpler layout (no flex wrapping concerns). Trade-off: visually divorces the clock from "the skill checks" the spec ties it to. Rejected.
